### The two bugs, in one paragraph each (so nobody re-derives them)

**The corruption.** `ExpertRAMCache.put_slab` had four decline paths (duplicate key, layer-evict
failure, global-evict failure, budget failure). Each called `arena.release(slab_idx)` and returned
normally — but the caller keeps using the views it passed in (`moe_patch._load_one` returns exactly
those views to the forward, which then DMAs from them). A declined insert therefore put a live
buffer back in the free list, the next `acquire()` handed it out, and io_uring overwrote it
mid-copy. Torn expert weights → NaN logits → `multinomial`'s inf/nan assert. `record_read()`'s
event guard could not help: the slab was freed *before* any read event existed, so `acquire()` had
nothing to synchronise on. **Two earlier fix rounds missed it because both hardened the
evict→reuse window; this is a different one.** The old guard message blamed worker-vs-worker races
inside `_stager_executor` and sent readers to the wrong subsystem for six weeks — it was
stager-vs-MAIN-thread all along.

**The duplicate reads.** The stager and the decode miss path both did "is it cached? no → read
~11.8 MB off NVMe → insert". Check-then-act: whoever lost the insert race had already paid for the
read and threw the bytes away — ~200 stager and ~190 decode wasted reads per token. Fixed with an
in-flight claim (`ExpertRAMCache.claim_load` / `peek_load` / `mark_running` / `finish_load`).

### P3 · [x] Tiny reads — **BUILT AND REFUTED 2026-08-30. ROW CLOSED.**

Every expert read is bimodal: one bulk contiguous group (11.80 MB Qwen / 8.85 MB MiniMax) plus
1–2 tiny groups (~0.04 MB) holding scales/bias. The tiny reads carry **0.3–0.4 % of the bytes**.

| | lookahead OFF | lookahead ON |
|---|---|---|
| tiny-read occupancy | 2.84 s (5.7 % of decode) | **20.56 s (46.4 % of decode)** |
| per tiny read | 0.18 ms | **1.09 ms** |

Queueing behind a busier ring pool explains *some* of a 6× inflation, but it was not chased and
should not be assumed to explain all of it. **Cheap idea recorded but NOT costed:** these are the
same scales/bias on every read of an expert, and all of them together are only ~0.5 GB on Qwen —
small enough to hold resident and never read again, which would remove 100 % of the tiny reads.

**REFUTED 2026-08-30 — the store was built, it works, and it is SLOWER. Do not rebuild it.**
Holding the tiny groups resident removes 100 % of the tiny reads (21 168 / 42 956 / 51 190 → 0),
fills to 455.9 MB on Qwen inside one 64-token arm, and returns byte-identical greedy ids — and
costs **−2.7 % at N=1, −11.3 % and −14.5 % at N=3**. Every N=3 store-off arm beat every store-on
arm with no overlap.

Mechanism, from the read traces: the tiny reads were **staggering the 8-worker ring pool**, not
stealing capacity from it. A worker's cycle was a 1.6 ms tiny read then a ~9 ms bulk read, so the
pool's bulk reads spread across k=3–7 in flight. Remove them and the workers synchronise — dead
time 24.8 % → 29.9 %, all-eight-busy 4.3 % → 15.4 %, per-bulk-read latency 9.12 → 10.36 ms, and
aggregate bandwidth 4.267 → 3.877 GB/s. NVMe bandwidth is concurrency-dependent, so a burstier
pattern reads the same bytes slower.

**The figure that misled this row — "a ring held 91.7 % of decode for 0.3 % of the bytes" — is
true and does not mean waste.** Occupancy is not contention. Read COUNT is a resource: a small
interleaved read that keeps the drive's queue non-empty is worth more than the ring-time it holds.
Any future change that removes reads must measure the bandwidth-vs-concurrency curve, not bytes
and occupancy alone. **The ~5.12 GB/s ceiling P1 found is therefore still unexplained — it is not
the tiny reads.** Full trail: `plans/2026-08-30-P3-tiny-store-RESULTS.md`.

### P4 · [ ] Prefetch admission policy — the residual +17.8 % bytes

After the reservation, lookahead still reads 221.84 GB against a 188.24 GB baseline (+17.8 %) per
64 tokens. That residual is **eviction churn**: prefetched layer-N+1 experts evict layer-N experts
that are still needed, and both get re-read. Approaches: a reserved prefetch sub-budget, or
admitting prefetched entries LRU-cold rather than MRU-warm.
**Where — the row had no symbols until 2026-08-30; here they are.** Prefetched entries enter the
cache through `ExpertRAMCache.put(..., prefetch=True)` and `put_slab(..., prefetch=True)`
(`vaayu/persist/expert_cache.py:507` and `:559`), both of which land the key at the MRU end of
`self.cache` / `self._layer_caches[layer]` (`OrderedDict`, `:287`/`:291`) exactly like an on-path
miss; `_note_prefetch` (`:629`) records it in `self._prefetched` (`:303`) for hit accounting only —
**it does not affect eviction order today, and that set is where an LRU-cold admission would hook
in.** Eviction is `_evict_layer_oldest` (`:635`, oldest-first). The only caller is
`_load_predicted_expert` (`vaayu/moe_patch.py:1477`), fused-EXL3 forward only — so **P2 gates
whether this row can be measured on MiniMax at all.**
**Gate:** bytes/token down AND coverage held. Do not accept coverage alone.

**Headroom — the original figure is now SUSPECT, do not quote it.** It read: "at 6.05 GB/s while
covered and baseline bytes, full coverage implies ~2.0 tok/s against today's 1.422." That assumes
the bandwidth freed by better admission is actually available. P1 then found every lookahead-on
arm pinned at **~5.12 GB/s aggregate regardless of N** (six arms, three widths, 1 % band), and P3
showed that removing reads outright made bandwidth WORSE. If that ceiling binds, this row's
headroom is a fraction of 2.0 tok/s. **P8 must resolve the ceiling before this number is trusted.**

**P1 (2026-08-30) strengthens this row:** that +17.8 % residual is single-stream. Under fan-out it
is **+21.3 % at N=2 and +24.6 % at N=3**, and it is precisely why lookahead's benefit decays as
streams are added. Fixing admission is what would make P2 worth defaulting ON at any N.

## 4. Numbers you should not re-derive

**The `~5.5 GB/s NVMe` figure was WRONG and is corrected in `CLAUDE.md` §5 and `todo.md`.** It was
a measured-path number (roughly what the expert path achieves at 2–3 reads in flight) promoted to a
hardware constant and then used as a denominator. Every "% of the drive" written before
2026-08-30 is against the wrong number.

- Drive: **Samsung SSD 990 PRO 1TB, sequential-read spec 7.45 GB/s.**
- Bandwidth is **concurrency-dependent**, measured: 1 read in flight → 3.3 GB/s, 2 → 5.3, 3 → 6.5,
  **4 → 6.9**, still rising. Figures at k ≥ 5 exceed spec and are instrument artifact — quote k ≤ 4.
- Decode sits at **50–51 % of the drive**, not the 71–73 % on record.

**Reads are BIMODAL** — one bulk group per expert plus 1–2 tiny scale/bias groups. Any analysis
that averages across both populations is wrong; this is what made R2 look viable when it is not.

descriptors per layer" counted the tiny reads. In bytes there is ONE read per miss, and misses are
already dispatched one-future-each across 8 workers, so bulk concurrency is already at its
structural ceiling. All that was left was dropping the tiny group's round-trip: **~1.02×**. Do not
reopen it.

## 7. Measurement traps — each of these cost a whole matrix

1. **Decode greedily.** Sampling changes routing → changes bytes/token → changes tok/s.
   corr(GB/tok, tok/s) = **−0.997** on Qwen. A tok/s comparison under sampling measures routing luck.
2. **Make the ballast target reachable and HARD-FAIL when it is not.** The arena is sized from
   `psutil.virtual_memory().available` AT LOAD, and this box frees a little more RAM after each
   consecutive run, so unballasted back-to-back arms grow their cache and are not comparable. A gate
   that can only warn is not a gate.
3. **Gate on bytes/token, not slab count.**
4. **Do not bucket per-read when measuring bandwidth vs concurrency.** A read's duration decides
   both how likely it is to overlap others and how it is weighted, which fakes a plateau. Cut the
   timeline at every start/end instead and weight by time — that is what `probe_split.py` does.
   This single error made R2 look viable and inflated L1's lever estimate.
5. **Split bimodal populations before averaging anything.** See §4.
6. **"It did not crash" is the weaker corruption detector.** The NaN assert only fires when a torn
   slab happens to produce a NaN. Compare **greedy token ids** against a control run instead — a
   corrupted weight that merely shifts a logit changes a token without ever crashing.
7. **Verify a new test fails against the code it targets.** Both reservation behaviour tests passed
   on first run; mutating the code under them (backstop → 0; drop the `.running` check) proved they
   were load-bearing rather than vacuous.
